# حَرِّك | HARRIK — البرومبت التنفيذي الكامل (V1.1 → V2)

> **الغرض:** برومبت واحد جاهز لتسليمه لوكيل برمجة (AI Coding Agent) لتحويل HARRIK من نسخة V1.0 وظيفية إلى **تطبيق مؤسسي احترافي سلس** يعمل كتطبيق جوال حقيقي (PWA)، مع دخول مرة واحدة، بصمة، إشعارات موثوقة، وأون بوردنج احترافي.

---

## 0. الدور والسياق (Role & Context)

أنت مهندس برمجيات أول متخصص في **Next.js 15 (App Router) + React 19 + TypeScript + Supabase + Tailwind**. تعمل على مستودع قائم اسمه **HARRIK (حَرِّك)** — نظام ذكي للمواقف والتواصل مع أصحاب السيارات في المنشآت (مدارس/أبراج/مجمعات) في دولة قطر.

**الوضع الحالي:** V1.0 مكتملة وظيفياً (بحث باللوحة، تنبيهات مواقف، لوحة إدارة، استيراد CSV/XLSX، تقارير، تعدد مستأجرين، PWA، Web Push).

**المطلوب:** إغلاق كل الفجوات الوظيفية المذكورة أدناه، ثم تنفيذ طبقة التجربة الاحترافية (جلسة دائمة + بصمة + إشعارات موثوقة + أون بوردنج).

**اللغة والسياق:** التطبيق عربي أولاً (RTL) مع دعم إنجليزي (LTR) كامل. الأرقام العربية-المشرقية والإنجليزية متكافئة. التعليقات والواجهة ثنائية اللغة.

## 1. القيود التقنية الإلزامية (Hard Constraints)

- **Stack:** Next.js 15 App Router، React 19، TypeScript صارم، Tailwind، Supabase (`@supabase/ssr`, `supabase-js`).
- **النشر:** Cloudflare Workers عبر **OpenNext** (`@opennextjs/cloudflare`). لا تفترض نظام ملفات دائم ولا Redis خارجي.
- **حالة داخل الذاكرة غير موثوقة:** أي Rate Limiting أو عدّادات أو حجب يجب أن يكون **في قاعدة البيانات (RPC/جدول)** وليس `Map` في الذاكرة (لأن Workers تُشغّل عُزلاً متعددة).
- **الأمان:** الصلاحيات تُشتق دائماً من الجلسة على الخادم (`getAuthenticatedSession`) — لا تقبل `organization_id` أو `reporter_id` أو `recipient_id` من العميل أبداً.
- **RLS:** كل جدول جديد يجب أن يملك سياسات Row Level Security معزولة بـ `organization_id` + دالة `current_user_org_id()`.
- **عدم كسر التوافق:** لا تُغيّر عقود الـ API الحالية بما يكسر الواجهات؛ أضِف حقولاً/مسارات جديدة عند الحاجة.
- **الهجرات:** كل تغيير في المخطط يُضاف كملف هجرة جديد في `supabase/migrations/` بصيغة `YYYYMMDDHHMMSS_description.sql`، مع تحديث `src/types/database.types.ts`.

## 2. الجلسة الدائمة والدخول مرة واحدة فقط (Persistent Auth / Sign-in Once)

**الهدف:** المستخدم يسجّل الدخول **مرة واحدة** عند أول استخدام، ثم يبقى مسجّلاً لأشهر، ويُفتح التطبيق مباشرة دون إعادة إدخال كلمة المرور — مع الحفاظ على الأمان.

### المتطلبات
1. **جلسة طويلة الأمد:** اضبط عملاء Supabase (`client.ts` / `server.ts` / `middleware.ts`) على:
   - `persistSession: true`, `autoRefreshToken: true`, `detectSessionInUrl: true`.
   - كوكيز `httpOnly`, `secure`, `sameSite=lax`, `maxAge` طويل (مثلاً 400 يوم).
   - حدّث `middleware.ts` لتحديث الكوكيز باستمرار عبر `setAll` (موجود — تأكد من عدم فقد الجلسة).
2. **"تذكّر هذا الجهاز"**: خيار عند تسجيل الدخول (مفعّل افتراضياً). إن أُلغي، تنتهي الجلسة عند إغلاق المتصفح (`session` cookie).
3. **Refresh صامت:** عند فتح التطبيق، استخدم `supabase.auth.getSession()` أولاً (سريع، من الكوكيز) ثم `getUser()` للتحقق الخلفي — دون وميض شاشة تسجيل دخول.
4. **بوابة "قفل الجهاز" لا "تسجيل دخول":** عند إعادة الفتح، إن وُجدت جلسة صالحة + بصمة مُفعّلة → أظهر شاشة قفل سريعة (زر بصمة) بدل صفحة `/login`. إن لم تُفعّل البصمة → ادخل مباشرة.
5. **تسجيل الخروج الصريح** يمسح الجلسة والاشتراكات المحلية وحالة البصمة (مع سؤال تأكيد).
6. **إدارة الأجهزة/الجلسات:** صفحة بسيطة في `/profile` تسرد الأجهزة المسجّلة (من جدول الاشتراكات) مع زر "إنهاء الجلسة على هذا الجهاز".

### معايير القبول
- بعد أول دخول، إعادة فتح التطبيق (حتى بعد أيام) لا تُظهر صفحة تسجيل الدخول.
- إعادة تحميل الصفحة لا تُخرج المستخدم.
- انتهاء صلاحية الجلسة يُعيد الطلب لـ `/login?redirectTo=...` بسلاسة دون فقد المسار.

## 3. المصادقة الحيوية / البصمة (Biometric Unlock)

**الهدف:** فتح التطبيق ببصمة الإصبع/الوجه (WebAuthn / Passkeys) — تجربة تطبيق أصلي احترافية.

### المتطلبات
1. **المسار المفضّل:** استخدام **Supabase Auth Passkeys (WebAuthn)** إن كانت مفعّلة في المشروع — تسجيل `platform authenticator` كعامل مصادقة.
2. **المسار البديل (Local Device Unlock):** إن لم تتوفر Passkeys، نفّذ بوابة فتح محلية:
   - بعد دخول ناجح، اسمح للمستخدم بتفعيل "الفتح بالبصمة" من الإعدادات.
   - استخدم `navigator.credentials.create()` بمُصادِق المنصة (`authenticatorAttachment: "platform"`, `userVerification: "required"`) لإنشاء بيانات اعتماد محلية.
   - عند إعادة الفتح: اشترط `navigator.credentials.get()` (بصمة) **قبل** كشف الجلسة المحفوظة.
   - خزّن فقط معرّف المُصادِق (credential id) محلياً؛ **لا تخزّن أسراراً في `localStorage`** — الجلسة تبقى في الكوكيز الآمنة.
3. **الاكتشاف والتراجع:** إن كان الجهاز لا يدعم البصمة أو رُفض الإذن، اعرض كلمة المرور كخيار احتياطي دون تعطيل التطبيق.
4. **تفعيل/تعطيل** من `/profile` مع رسائل حالة واضحة، وإعادة التحقق عند التعطيل.
5. **القيود:** البصمة تعمل في السياق الآمن (HTTPS/PWA المثبّت)؛ اعرض حالة توضيحية عند عدم التوفر.

### معايير القبول
- عند فتح التطبيق PWA المثبّت، تظهر مطالبة البصمة ثم يدخل المستخدم خلال ثانية.
- رفض البصمة يسمح بالدخول بكلمة المرور.
- تعطيل البصمة يعمل فوراً.

## 4. الإشعارات الموثوقة (Reliable Push Notifications)

**الهدف:** وصول الإشعار حتى والتطبيق مغلق تماماً، وعلى شاشة القفل.

### المتطلبات
1. **Service Worker (`public/sw.js`):** تأكد من:
   - `push` event يعرض الإشعار دائماً (`event.waitUntil(self.registration.showNotification(...))`).
   - `notificationclick` يفتح المسار الصحيح (`/inbox` أو `/scan?...`) ويركّز النافذة.
   - `pushsubscriptionchange` يعيد التسجيل تلقائياً عبر `/api/push/subscribe`.
   - عدم تخزين `/login` أو `/platform` في الكاش (موجود — حافظ عليه).
2. **طلب الإذن في السياق الصحيح:** لا تطلب إذن الإشعارات عند أول تحميل؛ اطلبه بعد حدث ذي معنى (تفعيل من الإعدادات أو بعد أول بحث ناجح) مع شرح عربي واضح.
3. **إشعارات iOS:** أضف تعليمات "أضِف إلى الشاشة الرئيسية" لأن iOS يشترط PWA المثبّت لـ Web Push.
4. **تنظيف الاشتراكات المنتهية** (موجود في `/api/push/send`) — طبّقه أيضاً في مسار `/api/alerts`.
5. **إشعارات داخل التطبيق (In-App Notification Center):** أضف مركزاً موحّداً (شارة عدّاد + قائمة) يعرض كل التنبيهات حتى لو لم يُسمح بالإشعارات الخارجية.

### معايير القبول
- إشعار تنبيه موقف يظهر وشاشة الهاتف مقفلة والتطبيق مغلق.
- النقر يفتح `/inbox` على التنبيه الصحيح.
- إعادة تثبيت/تحديث SW لا تفقد الاشتراك.

## 5. قناة إشعار احتياطية (Fallback Notification Channel) — فجوة حرجة

**المشكلة:** التنبيه يعتمد كلياً على Web Push؛ إن لم يكن المالك مشتركاً، لا يصل أحداً.

### المتطلبات
1. **تصعيد تلقائي (Escalation):** إن لم يوجد اشتراك Push نشط للمالك خلال مدة (مثلاً 60–90 ثانية دون `acknowledged`)، فعّل:
   - إشعاراً للأمن/الإدارة (Push + In-App).
   - وخيار إرسال **SMS** عبر مزوّد (Twilio / Unifonic / Ooredoo) إن كان مضبوطاً في الإعدادات.
2. **قياس زمني:** استخدم جدول/دالة لتتبّع "أقدم تنبيه معلّق" ودفع التصعيد.
3. **قناة البريد:** دعم بريد للملخّصات والتقارير (اختياري لكن مُهيّأ بمزوّد قابل للتبديل).
4. **تجريد المزوّد:** طبقة `lib/notifications/channels/` بواجهة موحّدة (`sendSms`, `sendEmail`, `sendPush`) مع مزوّدات قابلة للتبديل عبر متغيّرات البيئة، وتعطيل آمن عند غياب المفاتيح.
5. **تفضيلات المستخدم:** لكل مالك تفضيل قناة (Push فقط / Push + SMS) في `/profile`.

### معايير القبول
- إنشاء تنبيه لمالك غير مشترك بالـ Push → يظهر إشعار للأمن تلقائياً.
- إرسال SMS يظهر في سجل التدقيق عند تفعيل المزوّد.

## 6. ربط الإعدادات بالتنفيذ فعلياً (Settings Must Actually Work) — فجوة حرجة

> حالياً عدة إعدادات تُحفظ في اللوحة لكنها **لا تُطبَّق**. اجعلها فعّالة:

1. **وضع الخصوصية Mode A / B / C:**
   - `api/search/route.ts` و`VehicleResultCard` يجب أن يقرآ `system_settings.privacy_mode` من قاعدة البيانات ويُطبّقاه:
     - Mode A: عرض كامل (الاسم + الجوال + الأزرار).
     - Mode B: إخفاء رقم الجوال، إظهار الاسم فقط + قناة "أرسل تنبيهاً" بدل الاتصال المباشر.
     - Mode C: إخفاء هوية المالك بالكامل (إظهار القسم فقط) مع تمكين التنبيه فقط.
   - طبّق الإخفاء **على الخادم** (لا ترسل الحقول المخفية من الأساس).
2. **تفعيل/تعطيل البحث الجزئي + الحد الأدنى للأرقام:** اقرأهما من `system_settings` ومرّرهما إلى `validatePlateQuery` بدل القيمة المثبّتة `3`.
3. **قالب واتساب المخصّص:** `lib/whatsapp.ts` يجب أن يستخدم القالب من الإعدادات (مع متغيّرات `{plate}`, `{venue_name}`) والرجوع لقالب افتراضي عند غيابه.
4. **أنواع التنبيهات:** `CreateAlertDialog` يجب أن يجلب الأنواع من `parking_alert_types` الخاصة بالمنشأة (بدل تثبيت 5 أنواع في الكود)، مع fallback للافتراضية.
5. **ساعات العمل/الذروة:** استخدمها لحساب "ساعة الذروة" فعلياً في التقارير ولوحة التحكم.

### معايير القبول
- تغيير Mode C يخفي رقم المالك فوراً في البحث (تحقق من عدم إرساله في الاستجابة).
- تعطيل البحث الجزئي يمنع نتائج اللاحقة.
- تعديل قالب واتساب يغيّر نص الرسالة المُولّدة.
- إضافة نوع تنبيه جديد في الإعدادات يظهر في نافذة إنشاء التنبيه.

## 7. إغلاق فجوات المنطق والأمان (Logic & Security Gaps)

1. **إزالة بيانات الاختبار من مسارات الإنتاج:**
   - `SEED_VEHICLES` في `api/search` و`KNOWN_TOKENS`/`MOCK_TOKEN_VEHICLES` في `api/scan/*`.
   - انقلها إلى `tests/fixtures` أو خلف علم بيئة (`ENABLE_TEST_FIXTURES=true`) لا يعمل في الإنتاج. لا ترجع بيانات وهمية عند فشل Supabase — أرجع خطأ صريحاً.
2. **Rate Limiting دائم:** انقل `RECENT_ALERTS` (Map في الذاكرة) إلى جدول/RPC في Postgres (نافذة 5 دقائق لكل permitToken/vehicle).
3. **إصلاح خطأ FK للزوار:** في `api/scan/alert` يُمرَّر `vis.id` (تصريح زائر) كـ `vehicle_id`. أضِف عموداً `visitor_pass_id` أو اجعل `vehicle_id` nullable مع علاقة صحيحة، دون كسر المخطط.
4. **حماية الإساءة على `/scan` العام:** أضِف Cloudflare Turnstile أو حدّ معدل بالـ IP (في DB) لمنع الإغراق.
5. **ترقيم الصفحات والتصفية من الخادم:** `api/alerts` و`api/unknown` و`api/admin/staff|vehicles` — أضِف `limit/offset` + بحث/تصفية على الخادم. حدّث الواجهات لتحميل تدريجي (Infinite/pagination).
6. **تحويل بلاغ السيارة المجهولة إلى مسجّلة:** أضِف مسار "ترقية" يُنشئ مركبة/مالك من البلاغ ويحدّث البلاغ إلى `resolved` مع ربطه.
7. **إدارة الجلسات:** جدول يعرض الجلسات/الأجهزة النشطة (يرتبط بنقطة 2.6).
8. **سجل تدقيق موحّد:** تأكد من تسجيل كل عمليات: إنشاء/تعديل كادر، مركبة، تنبيه، تغيير إعدادات، إرسال إشعار.

### معايير القبول
- لا وجود لأي بيانات وهمية قابلة للوصول في الإنتاج.
- حدّ المعدل مُطبَّق عبر إعادة تشغيل Worker (لأنه في DB).
- قائمة التنبيهات تُحمّل 20 سجلاً افتراضياً مع "تحميل المزيد".

## 8. المصادقة: استعادة كلمة المرور والدعوات (Auth Lifecycle)

1. **دعوات الكادر:** عند إنشاء موظف في `api/admin/staff`:
   - استخدم `admin.inviteUserByEmail()` أو `generateLink` لإرسال دعوة بدل تعيين `Password123!`.
   - ألزم المستخدم بتعيين كلمة مرور عند أول دخول.
2. **نسيت كلمة المرور:** صفحة `/forgot-password` + `/reset-password` باستخدام `resetPasswordForEmail` وتدفّق الاستعادة عبر Supabase.
3. **رسائل بريد مخصّصة بالعربية** (قوالب Supabase) لـ: الدعوة، الاستعادة، تأكيد البريد.
4. **فرض قوة كلمة المرور** وتحقق من التكرار عند التغيير.

### معايير القبول
- إنشاء موظف جديد يرسل دعوة بالبريد ولا يضع كلمة مرور معروفة.
- تدفّق "نسيت كلمة المرور" يعمل من البداية للنهاية.
- لا توجد كلمة مرور افتراضية في الكود.

## 9. الأون بوردنج الاحترافي لتسجيل المنشآت الجديدة (Onboarding)

**الهدف:** تدفّق تسجيل منشأة جديدة (SaaS) احترافي متعدد الخطوات، سلس وواضح.

### التدفّق المقترح (Wizard)
1. **الشاشة الترحيبية:** عرض قيمة النظام (Find. Contact. Move.) + زر "ابدأ التسجيل".
2. **بيانات المنشأة:** الاسم بالعربية/الإنجليزية، النوع (مدرسة/برج/مجمع/وزارة/مستشفى)، الدولة (قطر افتراضياً)، المنطقة الزمنية، الشعار (رفع اختياري).
3. **الهوية البصرية (Branding):** الألوان، اسم المكان (`venue_label`)، رقم أمن البوابة.
4. **إنشاء حساب المدير:** الاسم، البريد، الجوال، كلمة المرور (أو دعوة).
5. **التحقق:** تأكيد البريد (OTP/رابط) — خطوة إلزامية.
6. **الإعداد الأولي:** إنشاء الأقسام، اختيار وضع الخصوصية، قالب واتساب، تفعيل البحث الجزئي.
7. **الاستيراد الأول (اختياري):** رفع ملف CSV/XLSX للكادر والسيارات، أو تخطٍّ.
8. **الختام:** شاشة نجاح + معاينة QR للتصاريح + CTA "ابدأ الاستخدام".

### المتطلبات التقنية
- جدول/حالة أون بوردنج مرتبطة بـ `organizations.status = 'onboarding'` (موجود في مخطط تعدد المستأجرين — فعّله بالكامل).
- **حفظ تدريجي** لكل خطوة (استئناف لاحق إن انقطع المستخدم).
- خلف واجهة نظيفة: تقدّم مرئي (Stepper)، تحقق فوري من المدخلات، رسائل خطأ عربية واضحة.
- منع الدخول التشغيلي قبل اكتمال الأون بوردنج (`status='active'`) — باستثناء خطوات الأون بوردنج نفسها.
- **لوحة المنصة (`/platform`)** تُظهر المنشآت الجديدة بحالة `onboarding` وتتيح التفعيل/التعليق (موجود جزئياً — أكمل التفعيل المباشر).

### معايير القبول
- منشأة جديدة تُنشأ وتُفعّل من البداية للنهاية دون تدخّل يدوي.
- يمكن استئناف الأون بوردنج إن أُغلق المتصفح.
- لا يستطيع مستخدم منشأة `onboarding` الوصول لصفحات التشغيل.

## 10. التعريب الكامل والاتساق (Full i18n)

1. انقل **كل** النصوص المثبّتة (صفحات `admin/reports`، `scan`، وبعض الإداريات) إلى `src/i18n/translations.ts`.
2. تأكد أن تبديل اللغة يغيّر **كل** الشاشات فعلاً، بما فيها التقارير المطبوعة (اختر اللغة عند الطباعة).
3. الاتساق: الأرقام، التواريخ (`ar-QA`)، الاتجاهات (`dir="rtl"`/`ltr`)، والخطوط.

### معايير القبول
- لا يوجد نص عربي مثبّت في مكوّنات مشتركة؛ وضع English يترجم كل شيء.

## 11. تجربة الاستخدام السلسة (Smooth / Professional UX)

1. **PWA مؤهّل للتثبيت:** `manifest.json` كامل، أيقونات، `display: standalone`، شاشة بداية، وتشجيع التثبيت (`PWAInstallPrompt` موجود — حسّنه).
2. **حالات التحميل:** Skeleton loaders بدل الشاشات الفارغة في كل الصفحات.
3. **UI تفاؤلي (Optimistic):** تحديث حالة التنبيه (استلام/حل) فوراً مع تراجع عند الفشل.
4. **حالات الخطأ والفراغ:** رسائل عربية واضحة + إجراء مقترح (retry / إجراء بديل) في كل شاشة.
5. **العمل دون اتصال جزئياً:** كاش للقراءة فقط للبيانات غير الحساسة + بانر "أنت غير متصل".
6. **الأداء:** Lazy-load للمكوّنات الثقيلة (`tesseract.js`, `recharts`)، تحسين الصور، تقليل JS الأولي، `Suspense` مناسب.
7. **إتاحة (a11y):** تنقّل لوحة المفاتيح، تسميات ARIA، تباين ألوان كافٍ، أحجام لمس ≥ 44px.
8. **الأخطاء:** حدود خطأ (Error Boundaries) + تسجيل مركزي (Sentry أو ما يعادله) دون كشف بيانات شخصية.
9. **الاستجابة:** مثالي للهاتف أولاً (Mobile-first)، ويعمل بسلاسة على التابلت وسطح المكتب.

### معايير القبول
- Lighthouse PWA/Accessibility/Performance ≥ 90 على الجوال.
- لا شاشة بيضاء أو خطأ غير مُعالج في أي مسار.

---

## 12. الأمان والصلاحيات (Security & RBAC)

1. تحقق من تطبيق الأدوار: `staff` / `security` / `admin` / `super_admin` + `platform_admins` على **كل** نقطة API وكل صفحة (بما فيها الجديدة).
2. **حدّ من تسريب PII:** لا تُرجع حقول المالك في أي استجابة لا يحتاجها الدور/وضع الخصوصية.
3. **حماية النقاط العامة:** `/scan` و`/api/scan/*` (Turnstile + rate limit في DB).
4. **تدقيق كامل** لكل إجراء حساس.
5. **أسرار البيئة:** لا مفاتيح في الكود؛ تحقق من عدم تسريب `SUPABASE_SERVICE_ROLE_KEY` للعميل.
6. تحقق من سياسات RLS لكل جدول جديد (اختبارات تلاعب بين مستأجرين).

### معايير القبول
- اختبار: مستخدم من منشأة A لا يرى أي بيانات من منشأة B (عبر API و RLS).
- لا توجد بيانات وهمية أو أسرار في حزمة العميل.

## 13. الاختبارات (Testing)

- **وحدة:** تطبيع اللوحات، القوالب، i18n، منطق الخصوصية (Privacy Mode mapping).
- **تكامل:** مسارات API (بحث/تنبيه/استيراد/أون بوردنج/دعوات) مع التحقق من الأدوار والعزل بين المستأجرين.
- **E2E:** تدفّق كامل: دخول مرة واحدة → بصمة → بحث → تنبيه → وصول الإشعار → حل → تقرير. وتدفّق أون بوردنج كامل.
- حافظ/حدّث الاختبارات الموجودة تحت `tests/` (لا تُسقط تغطية قائمة).

## 14. معايير الإنجاز النهائية (Definition of Done)

- [ ] لا يوجد إعداد في اللوحة يُحفظ دون أن يكون فعّالاً في السلوك.
- [ ] الدخول مرة واحدة + بصمة يعملان على PWA المثبّت (Android + iOS).
- [ ] إشعارات تصل والتطبيق مغلق، مع قناة احتياطية للمالكين غير المشتركين.
- [ ] صفر بيانات اختبار/وهمية في مسارات الإنتاج.
- [ ] Rate limiting في قاعدة البيانات (يصمد عبر إعادة تشغيل Worker).
- [ ] أون بوردنج كامل قابلاً للاستئناف + تفعيل من لوحة المنصة.
- [ ] استعادة كلمة المرور + الدعوات تعمل بالبريد.
- [ ] تعريب كامل + تبديل لغة لا يترك نصوصاً مثبّتة.
- [ ] RLS + عزل مستأجرين مُختبران.
- [ ] `pnpm lint`, `pnpm test`, `pnpm build` تمرّ نظيفة.
- [ ] لا كسر لأي عقد API أو شاشة قائمة.

## 15. ممنوعات (Anti-Goals)

- لا تعِد كتابة النظام من الصفر — ابنِ فوق البنية القائمة.
- لا تُدخل حالة دائمة داخل ذاكرة Worker.
- لا تعتمد على العميل في أي قرار صلاحية أو عزل مستأجر.
- لا تعرض بيانات المالك عند تفعيل وضع خصوصية مُقيّد.
- لا تُبقِ كلمات مرور افتراضية أو بيانات وهمية في مسارات الإنتاج.
